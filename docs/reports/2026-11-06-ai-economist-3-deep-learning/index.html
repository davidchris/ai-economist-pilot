This post assumes you are comfortable with regression, regularization and cross-validation, and have only a passing knowledge of neural networks. It builds up the exact model in pilot/model.py, layer by layer, using its real sizes. Part 4 covers how it learns without labels. Here, assume something hands us a loss to minimise.

Start from what you know: multinomial logit

A worker must choose one of 50 actions at each step. If this were a classification problem you might fit a multinomial logit. For observation x, each action a gets a score, and a softmax turns the scores into probabilities:

P(a | x) = exp(βa′x) / Σb exp(βb′x)

The score vector is called the logits. The last layer of our network is exactly this model. Everything before it replaces the raw x with learned features φ(x). In a tabular project, you might hand-build those features or let gradient boosting find interactions. A neural network fits φ and β jointly, by the same gradient-based procedure.

That is a good way to hold the whole thing in your head: a logit model on top of a feature extractor, trained end to end.

Learning the features: dense layers

A dense layer is a set of linear regressions with shared inputs, each passed through a simple nonlinearity. Using the ReLU function, max(0, t):

h = max(0, W x + b)

A single layer with 128 units means 128 such outputs, so the weight matrix has 265 × 128 = 33,920 entries plus 128 intercepts, which matches the parameter counts in the model. Stacking layers lets later ones combine earlier features, producing piecewise-linear functions and interactions with no manual specification. Without the nonlinearity, stacked layers would collapse back into one linear model.

Fitting works by gradient descent: compute the loss on a small batch, get its derivative with respect to every parameter using the chain rule (this is all "backpropagation" means), and take a small step downhill. There is no closed form and no convexity guarantee, and in practice it works well anyway.

You will also see layer normalization after the dense layers. It standardizes a layer's outputs for each sample, just as you might standardize inputs before regression, and it keeps the numbers feeding the LSTM in a stable range as the weights change.

What goes into the network

A worker never sees the whole world. Its observation has three parts:

  • Local map, 7 channels of 11×11. Think of 7 stacked spreadsheets centred on the worker: wood, stone, the two kinds of source tile, water, houses, and a mask showing which cells lie inside the world.
  • ID map, 2 channels of 11×11. Codes showing which agent is where and who owns what. These are categories, so a code of 3 is not "three times" a code of 1.
  • Flat features, 137 numbers. Foundation's flattened scalars and vectors, as follows.

Skill is in the flat vector, and this is what allows a single shared network to act differently for different workers, as discussed below. The planner's input leaves those private fields out.

Reading a map: embeddings and convolutions

Embeddings handle the ID codes. You might one-hot encode a categorical in a regression. An embedding instead gives each category a short vector of parameters learned during training, similar in spirit to target encoding except that it is fitted against the final objective. Here there are 100 possible codes × 4 dimensions = 400 parameters. The two ID channels become 8 channels of real numbers, and joining them with the 7 map channels gives 15 channels in total.

Convolutions handle spatial structure. Flattening an 11×11 grid into a regression would make "wood directly north" a completely different feature from "wood two tiles north-east", and it would take many parameters to learn each pattern at each place. A convolution slides a small set of 3×3 filters across the grid, applying the same parameters at every location. The first layer has 16 filters over 15 channels, so its weights number 3 × 3 × 15 × 16 = 2,160. A stride of 2 skips every other position, which compresses the map: 11×11 becomes 5×5, then 2×2 with 32 filters, for 128 numbers. Those summarise what is nearby.

Notice how few parameters this needs: about 7,000, or under 4% of the network.

Remembering: the LSTM

A regression treats every row independently. That is a poor fit here. The worker sees only a local window, so it has to remember where the wood was. Tax timing matters too: a tax period's rates and income accumulate over 100 steps, and the sensible action depends on what has happened so far.

An economist can read a Long Short-Term Memory layer as a nonlinear state-space model with learned dynamics. It keeps a hidden state vector of 128 numbers and, at each step, uses the current input and the previous state to compute:

  • how much of the old state to keep (a forget gate, a learned value from 0 to 1 per dimension),
  • how much new information to add (an input gate), and
  • what to output for this step (an output gate).

The gating is what allows information to persist across many steps without being washed out. This layer is by far the largest in the model, with two-thirds of the parameters:

Training a memory model on sequences brings some bookkeeping. Each 200-step rollout is cut into 50-step sequences, and gradients flow only within a sequence, which is known as truncated backpropagation through time. Each sequence starts from the hidden state that was stored during collection, and memory resets to zero when an episode ends. If any of that goes wrong, the model silently trains on the wrong history. So before every update the trainer re-runs the stored sequences and requires that action probabilities match the ones recorded during collection, within 1 × 10⁻⁴. The largest error seen in the final pretraining runs was 4.77 × 10⁻⁶.

Valid actions only: masking

You cannot build without materials or walk into water. Foundation supplies a 50-element mask at each step, and the network sets the logit of every disallowed action to −10⁹ before the softmax, making its probability effectively zero. This one line in the model saves the learner a huge amount of exploring actions that do nothing, and it also lets the rules restrict the planner: its tax-rate ceiling is enforced through masks in exactly this way.

Two networks, shared across workers

Reinforcement learning methods of this type need two predictions at every step: a policy (what to do) and a value (how well things are expected to go from here). Part 4 explains why. The two could share layers, but here they do not. They are two separate towers with the same structure, each with its own LSTM. The value tower ends in a single output, and that is the only structural difference.

All four workers use one set of weights, while each keeps its own LSTM memory. This parameter sharing is similar to pooling in a panel model. Each step gives four observations for one model, and workers still behave differently because their observations differ: skill, location and inventory are all inputs. As shown in Part 2, the shared network learns very different behavior by skill. The model is effectively a single conditional decision rule, with heterogeneity entering through its inputs.

The planner's network

The planner follows the same pattern with bigger sizes. It uses 256 units in place of 128, and it reads the full 25×25 map in place of an 11×11 window. Its convolutions produce 800 numbers, which join 119 flat features: 86 from Foundation, 8 public fields for each of 4 workers (inventory, location, last income and marginal rates), and time.

The one new idea is its output. It has to choose seven things at once, one rate per bracket. The output layer gives 154 scores, split into 7 groups of 22, and each group gets its own softmax. These are treated as independent, so their log probabilities and entropies simply add up. This turns 227, or about 2.5 billion, joint actions into 154 numbers, at the cost of being unable to directly represent "if the bottom rate is high, keep the next rate low". With 1,710,299 parameters, the planner's network is more than four times the size of the workers', yet it makes only one decision per 100 steps.

Adam is gradient descent with two extras: a running average of the gradient (momentum), and a separate step size per parameter, scaled by how noisy that parameter's gradient has been. It is the usual default and needs little tuning. Gradient clipping rescales any gradient with a norm above 10, which stops one bad batch from wrecking the weights.

Three things differ from fitting a typical model on a table:

  • The data keeps changing. Every batch is created by the current model. There is no epoch over a fixed dataset, and no stable train and validation loss curve to watch.
  • Early stopping and validation-loss curves do not apply. The loss has no absolute meaning, because the data moves underneath it. Progress is judged by running the policy on new episodes.
  • The GPU is barely used. In the first pilot it averaged 5% utilization, with peak tensor allocation under 200 MiB throughout the project. Collecting experience takes most of the time, at roughly 170 to 360 environment steps per second in the latest runs, so a bigger GPU would not speed up this project.

What went wrong, and how it showed up

Three episodes from the project's logs are worth studying, because the symptoms are unlike anything in tabular work.

A saturated critic

Early runs showed value-function explained variance stuck at about 0. A direct probe of one model found it predicting V = 17.31 for every agent after about step 100, regardless of the situation. There is a neat explanation. LSTM outputs are bounded in ±1, and the output layer is linear, so its largest possible output is limited by the size of its weights. By Cauchy-Schwarz the bound is ‖w‖ × √128, here about 1.55 × 11.3 ≈ 17.5. So the critic had pushed its output about as high as those weights allow, and a forecast that never changes explains nothing. The project treats this as consistent with saturation, since one direct probe does not prove the mechanism. It also turned out to be a slow start and not a dead end, because weights can keep growing given enough gradient steps.

More small steps beat fewer large ones

The first suspect for an early collapse was that batches were too small. The controlled test said the opposite. With labor cost removed and only the minibatch size varied, on one seed:

Only the smallest batch, with 16 optimizer steps per update, lifted the critic off its ceiling within this budget. With 4 economies each update has much less data than the paper's 60, so keeping the paper's batch size would mean only about one gradient step per update. This is a finding about small budgets. It does not show that the paper's batch size is wrong, and a minibatch of 200 means 16 times the paper's optimizer steps per transition.

A feature that was not missing

Upstream's model feeds every non-spatial, non-mask field into its dense layers, and this port's packing function originally kept only flat, ignoring the separate time field. The project recorded that as a defect, on the belief that workers could not see how far through an episode they were, and appended time, widening the input from 136 to 137. On one seed, held-out output at 400k moved from 1,002 to 1,134, which the project judged close to noise.

Checking this for the series turned up a correction. Foundation puts time in both places. Element 130 of the 136-long flat vector equals time at every step tested, over 400 steps of one episode. So workers could always see the clock, and the change added a duplicate input. Upstream's model concatenates both fields too, so 137 does match its input, but no new information arrived. That fits the small effect, and the main finding stands: the labor ramp caused the collapse either way. The lesson is familiar from tabular work: check a schema by looking at values as well as names. It also carried a real cost, because the wider input made all older checkpoints unusable.

Making a stochastic system trustworthy

A large part of the code exists so results can be believed. Because the run is chained from ten-minute segments, a checkpoint has to restore every piece of state: both models and optimizers, LSTM memories, every random number generator, and the complete simulator. On CPU, an interrupted-and-resumed run matches an uninterrupted one bit for bit. Files are fingerprinted so a changed trainer rejects old checkpoints, which is why even small trainer edits are expensive.

Numerical checks also caught something subtle. After every segment, the trainer confirms that GPU and CPU give the same forward results within a tolerance combining relative 1 × 10⁻⁴ and absolute 1 × 10⁻⁵. One check failed by a hair: a difference of 1.16 × 10⁻⁵ on a critic value near 0.007, in a forward pass where the largest value was 19.8. Values close to zero only get the absolute tolerance. Collapsed economies produce critic values near zero, so this happened far more often there, at 14 of 330 learned-tax segments and 0 of 660 others. The policy check never failed, and evaluation does not use the critic. The project's response was to accept and record those specific failures, and to scale the tolerance when the trainer next has to change, which matters because it invalidates checkpoints that took hours to create.

What to remember from this post

The network is a logit model on learned features. Convolutions read the map, the LSTM remembers, masks enforce the rules, and two towers separately estimate behavior and value. Its failure signals, such as an R² of zero or a forecast that never changes, are diagnosable with ordinary statistical thinking. What comes next is how the loss itself gets defined when no one provides labels.
