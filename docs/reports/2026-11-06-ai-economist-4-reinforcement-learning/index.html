In Part 3 we built a network that outputs action probabilities and said something would give it a loss. This post supplies that loss, shows how the whole thing runs in this project, and walks through the two collapses that have defined its progress. The code in question is pilot/train.py and the advantages function in pilot/model.py.

Learning with no labels

Supervised learning needs someone to say which action was right. Here nobody knows. Is moving north correct at step 412? It depends on where the wood is, what the others are doing, what the tax will be and how the agent will act later. All we get is a stream of rewards, often long after the choices that earned them. A house pays immediately, for example, but only after dozens of steps of walking and gathering that each cost a little.

Reinforcement learning solves this with a simple plan: act, see how it went, and make whatever went better than expected more likely. The rest of this post is that sentence with the details filled in.

The problem, in dynamic-programming terms

You likely know the Bellman equation from macro. The value of being in a state is the expected reward now plus the discounted value of where you land next:

Vπ(s) = Eπ[ rt + γ Vπ(st+1) | st = s ]

In macro you know the transition function and solve this with value iteration on a grid. Here three things rule that out. The transition function is a large simulator with other learners inside it. The state is enormous. And each worker only sees part of it, which is why the policy has memory. So we are model-free: we only sample from the environment by running it.

The discount factor is γ = 0.998 per step, which gives an effective horizon of about 1/(1−γ) = 500 steps. That is long enough to span five tax periods and half an episode.

The policy gradient is a weighted logit

Think about fitting multinomial logit by maximum likelihood. You maximise Σ log P(observed choice | x). The policy gradient method does almost the same thing, using two substitutions:

  • The "observed choice" is the action the policy itself just sampled.
  • Each observation is weighted by an advantage A, which says how much better that action turned out than the policy expected. It can be negative.
maximise   Σt At · log π(at | st)

If an action beat expectations, its log-probability goes up. If it fell short, the negative weight pushes it down. A theorem (the policy gradient theorem) says that in expectation this really is the gradient of expected return, so this is a true optimisation and not just a heuristic. In practice each sample is extremely noisy, which is why everything else in this post exists.

The critic: a control variate

What should "expected" mean? We train a second network, the critic, to predict future discounted return from the current observation, as an ordinary regression. Subtracting that prediction from what actually happened leaves a much less noisy signal. Statisticians will recognise this as a control variate: you subtract a correlated quantity with known mean, which keeps the expectation but reduces the variance.

The critic is therefore the part of the system you can evaluate with familiar tools. Its explained variance is an R², and this is how the project detected a broken critic (see Part 3). The two-network pairing is why these methods are called actor-critic.

Advantages: a bias-variance dial

There are two extreme ways to measure how an action went. Take the actual return all the way to the end, which is unbiased but very noisy. Or take one real reward and trust the critic after that, which has low variance but inherits critic errors. Generalized Advantage Estimation interpolates using a single parameter λ. First define the one-step surprise:

δt = rt + γ V(st+1) − V(st)     At = δt + γλ At+1

With λ = 0 you get the low-variance end, and with λ = 1 the full-return end. This project uses 0.98, close to full returns. The recursion runs backwards through time, and the code is short enough to read:

def advantages(rewards, values, dones, bootstrap, gamma=0.998, lam=0.98):
    result = torch.zeros_like(rewards)
    carry = torch.zeros_like(bootstrap)
    next_value = bootstrap
    for t in reversed(range(len(rewards))):
        continuation = 1 - dones[t]
        delta = rewards[t] + gamma * continuation * next_value - values[t]
        carry = delta + gamma * lam * continuation * carry
        result[t] = carry
        next_value = values[t]
    return result, result + values

A worked example, with made-up numbers. Suppose a worker has three steps with rewards 0, 0, 5, critic values 10, 11, 10, and the critic values the state after that at 12. Working backward with γλ ≈ 0.978:

StepδAdvantage
35 + 0.998×12 − 10 = 6.986.98
20 + 0.998×10 − 11 = −1.02−1.02 + 0.978×6.98 = 5.80
10 + 0.998×11 − 10 = 0.980.98 + 0.978×5.80 = 6.65

Step 2 looks bad on its own, with a negative surprise, but the payoff one step later earns it a positive advantage. This is how a reward reaches back to credit the walk and the gathering that came before it.

Before use, advantages are standardized to mean 0 and unit variance, so the policy step does not depend on the reward's scale.

PPO: small, safe steps

This data comes from the current policy, so if the policy moves far, the data stops describing it. A big enough bad step can also wreck behavior, and then the learner has only bad data to learn from. Proximal Policy Optimization deals with this by removing the incentive to move too far. With ratio ρ = πnew(a|s) / πold(a|s), it uses:

Lpolicy = −mean[ min( ρ A, clip(ρ, 0.7, 1.3) A ) ]

When a ratio moves beyond ±30% in the favourable direction, the clipped term takes over and the gradient for that sample goes to zero. The total loss per minibatch, as written in the code, is:

loss = policy_loss + 0.05 * value_loss - entropy_coefficient * entropy

The value term trains the critic with squared error. The entropy term rewards keeping the action distribution spread out. That is a form of regularization that keeps exploration alive. A policy that collapses to one action too early can never find out that another action was better. The worker coefficient is 0.025. The planner's is 0.1 in the paper profile, from the paper's Table 2. You will see below why that number is under suspicion.

Watch how the workers change during pretraining. The maximum entropy for 50 actions is ln 50 = 3.91, and values fall as behavior becomes more decisive, here on seed 42:

One update, in real numbers

At about 270 environment steps per second, each update takes about 3 seconds. For scale, the paper's phase two has 400M steps. At this project's first-pilot rate, which is a smaller setup, that would take about 24.5 days per seed, before planner overhead. Learned-tax runs here ran at 169–222 steps per second, and the final comparison took about 19.4 hours in total and 37 GiB of results.

Two levels of learning

With five learners, each one's environment contains the others, so nothing is stationary. Workers share one policy, which pools their experience, but each still faces others who keep changing. The bigger issue is the worker-planner relationship. That gives the problem its two levels: an outer learner (the planner) and an inner population (workers) that respond to it. It resembles a Stackelberg game, with one important difference from the textbook. The followers are not at a best response when the leader moves, only partway through learning one.

The curriculum handles this in two stages, which the project implements with these details:

  • Phase one: free market, workers only. Labor cost weight rises as w = 1 − exp(−I / k), where I counts steps with positive mean worker reward in each economy.
  • Transition: worker model and Adam optimizer state carry over. Economies, memories and step counters start fresh, and labor cost is exactly full.
  • Phase two: workers keep learning. The planner starts with random weights at a learning rate of 1 × 10⁻⁴. Its rate ceiling rises from 10% to 100% over 3.6M steps.

The key experimental design: free-market, fixed-tax and learned-tax arms all go through the same transition from the same checkpoint, so differences come from the treatment.

Failure one: the labor ramp

On 4 November, a run with paper-aligned settings produced this per-20,000-step output during pretraining: 277, 26, 19, 22, 18, 8, 0.7, 0.6, 0, 0. Workers learned to do nothing, before the planner even existed. Compressed budgets and small batches both looked guilty.

A controlled screen found the cause. In labor-free runs the integrator I rises about 150 per episode, per economy. In that diagnostic the constant was k = 100, so the weight reached about 0.79 within one episode, while the policy was still nearly random and paying around 625 labor per worker. At that point every action carries a large immediate penalty, and the coin benefit is rare and delayed. So the critic and policy both learn that doing less is better. Once they do nothing, no building happens, and nothing shows them otherwise. That is an absorbing state, and it is the same shape as the later planner failure.

How results are judged

A training curve can look healthy while training conditions are easier than the real objective. That is exactly what a labor ramp does. So every result comes from held-out evaluation: weights frozen, a fresh economy with fresh memory, seeds never used in training, labor at full cost, tax ceiling removed, actions sampled from the policy. Development seeds (20000–20009) guide choices, and final seeds (30000–30009, then 40000–40009 for tax treatments) are touched only after the choices are fixed.

To define "productive" objectively, the project fixed a gate before any curriculum result existed. At each of the last two evaluated checkpoints:

  • The lower 95% bound of mean worker return must exceed the measured do-nothing return.
  • Mean output must exceed uniform random behavior.
  • Houses must get built.
  • The policy must have been trained at a labor weight of at least 0.95, not merely tested there.

Failure two: the planner stays random

From these gated checkpoints, the matched comparison ran 4.4M steps per arm. Part 2 has the economic results: free-market and fixed-tax arms stay productive and pass the gate, and learned-tax arms all fail it. From a learning perspective, the striking measurement is that the planner barely moved away from random.

So one story fits the observations, and it is an interpretation that has not been established. While the ceiling is low, near-random rates are harmless and output stays high. As the ceiling rises, the same near-random policy samples high, unpredictable rates. Workers respond by producing less, which is a sensible best response. Once production stops there is no income to tax and welfare stops changing, so the planner has no signal left. The system falls into an absorbing no-op state, as in failure one.

Why might the planner stay near uniform? The candidates are listed in the project's notes, and none has been tested:

  • Entropy coefficient. A value of 0.1, from the paper's table, may be strong relative to the learning signal.
  • Few decisions. One decision per 100 steps. By this series' arithmetic, 4.4M steps yields 44,000 tax decisions against 4M at the paper's budget, and only 8 per update, spread across 800 transitions.
  • A low learning rate, at 1 × 10⁻⁴.
  • Budget. About 1% of the paper's phase two, from 4 economies against 60.

The last one matters for interpretation. The tax ramp here reaches 100% after the same 900 completed episodes per economy as the paper, so four economies get far fewer samples along the ramp. The same schedule can therefore be much harsher here than it was in the paper, and this run does not contradict the paper's result.

The run itself also had rough edges, recorded in full in the project's log: the numeric check described in Part 3 tripped on collapsed arms, one driver bug caused a retried segment, and one log was overwritten. All of this is documented in TAX_COMPARISON.md, along with the replay checks run afterwards.

What gets tested next

  1. A uniform-random planner control. Remove learning, keep the ramp. If workers collapse just as before, near-random rates are sufficient to cause this and the story's first half holds. If they survive, that would point to the learning planner doing something worse than random, which would be a new puzzle.
  2. Planner settings at a fixed moderate ceiling. Test whether the planner can learn at all while the economy stays alive. The entropy coefficient and learning rate listed above are the obvious candidates to vary.
  3. Scaled critic tolerance, batched with those changes, because any change to train.py invalidates the current checkpoints and requires about 4.7 hours of pretraining across seeds.
  4. Keeping fixed tax versus free market provisional, since its contrast moved a lot between evaluation points.

Later milestones remain the same: a validated Saez baseline, ten seeds, larger budgets and convergence analysis over a final window. Only then would a comparison with the paper's 16% be meaningful.

The method in one paragraph

Run the current policy to generate data. Use a critic as a control variate to work out which actions beat expectations. Take a limited step in a weighted-logit objective that makes those actions likelier, with an entropy bonus that preserves exploration. Repeat thousands of times, with one learner nested inside another and curricula keeping the problem solvable. Then judge the result on episodes that training never saw, against tests written before the results existed. This project has that loop working for workers. Getting it to work for the planner is the open problem.

If you read one thing in the repository after this series, make it PRETRAINING_MILESTONE.md. It is a compact example of isolating a cause in a noisy learning system and keeping a clear record of what was not established.
